# Business Terms → Code Mapping

Every term in the bounded context glossary maps to a specific class or set of classes in the domain layer. This document traces each term to the exact file and explains what the code does to enforce the business meaning.

---

## Lead

> *"A potential customer who has expressed interest in a specific property through one of our portals. Each lead represents one inquiry."*

**Primary class**: `domain/model/Lead.java`

`Lead` is an aggregate root — the central object that owns the lifecycle of one customer inquiry. It holds all the information that arrived from the portal and enforces the only state transition the business allows.

```java
public final class Lead {
    private final LeadId id;
    private final CustomerContact customer;   // who is interested
    private final String propertyReference;   // which property
    private final City city;                  // where it is
    private final Instant receivedAt;         // when it arrived
    private final IdempotencyKey idempotencyKey;
    private LeadStatus status;                // NEW or ASSIGNED (mutable — the only one)
}
```

`status` is the only mutable field. All others are set at construction and never changed — a lead's customer, property, and city are facts that don't change after the inquiry arrives.

**Supporting classes**:
- `LeadId` — wraps `UUID`, generated by `LeadId.generate()` inside the use case
- `LeadStatus` — enum with exactly `NEW` and `ASSIGNED`

## Agent

> *"A real estate agent who handles customers in a specific city. Agents have a limit on how many new leads they can take on at once."*

**Primary class**: `domain/model/Agent.java`

`Agent` is the second aggregate root. It owns the eligibility decision — the only place an `Assignment` is ever created is inside `Agent.tryAssign()`. This means the capacity and city rules are enforced by the object itself, not by a caller.

```java
public static final int MAX_LEADS_PER_WINDOW = 5;
public static final Duration ASSIGNMENT_WINDOW = Duration.ofHours(24);

public Optional<Assignment> tryAssign(Lead lead, int currentLoadInWindow, Instant now) {
    if (!active) return Optional.empty();
    if (!city.equals(lead.city())) return Optional.empty();
    if (currentLoadInWindow >= MAX_LEADS_PER_WINDOW) return Optional.empty();
    return Optional.of(new Assignment(...));
}
```

The two business constants — "5 leads" and "24 hours" — live on the `Agent` class, not in configuration or the database. They are domain constants, part of the model.

**Supporting class**: `AgentId` — wraps `UUID`, non-null.

## Assignment

> *"The moment a lead is handed to a specific agent. Once recorded, this connection is permanent — we keep it as part of our history."*

**Primary class**: `domain/model/Assignment.java`

`Assignment` is immutable by construction — all four fields are `final`, there are no setters, and there are no methods that change state. Once created, it cannot be modified.

```java
public final class Assignment {
    private final AssignmentId id;
    private final LeadId leadId;      // which lead
    private final AgentId agentId;    // which agent
    private final Instant assignedAt; // when
}
```

The class has no `update()`, no `status`, no `cancelledAt`. The business says the connection is permanent — the code makes mutation structurally impossible.

`Assignment` is only ever created inside `Agent.tryAssign()`. No other path in the codebase can produce one.

**Supporting class**: `AssignmentId` — wraps `UUID`, generated by `AssignmentId.generate()`.

## Capacity

> *"The limit on how many leads an agent can take on at a time. No more than 5 new leads in the last 24 hours."*

**Where it lives**: `domain/model/Agent.java`, lines defining the two constants:

```java
public static final int MAX_LEADS_PER_WINDOW = 5;
public static final Duration ASSIGNMENT_WINDOW = Duration.ofHours(24);
```

**Where it is enforced**: `Agent.tryAssign()` receives `currentLoadInWindow` — the number of assignments the agent has received in the last 24 hours — and rejects if it is `>= 5`.

**How the load is counted**: in the use case, a single `GROUP BY` query counts assignments per agent since `now - 24h`. The result is passed into `tryAssign()` as `currentLoadInWindow`. The agent itself never queries the database — it receives the number as a parameter, keeping the domain free of persistence concerns.

**Supporting value in the domain service**: `AgentWithLoad` pairs an `Agent` with its pre-counted load so the routing service can compare loads across candidates without re-querying.

```java
public record AgentWithLoad(Agent agent, int currentLoad) { ... }
```

## City

> *"The geographic area a lead and an agent belong to. Leads are only routed to agents in the same city. Different spellings ('Milano', 'milano', 'MILAN') are treated as the same city."*

**Primary class**: `domain/model/City.java`

```java
public record City(String name) {
    public City {
        name = name.trim().toLowerCase(Locale.ITALIAN);
        if (name.isBlank() || name.length() > 128) {
            throw new IllegalArgumentException(...);
        }
    }
}
```

Normalisation to lowercase (using Italian locale) happens at construction — before any comparison, before any persistence write. `new City("Milano")`, `new City("MILANO")`, and `new City("  milano  ")` all produce the same object with `name = "milano"`. The glossary's requirement that different spellings are treated as the same city is enforced at the value object level, not by remembering to call `.toLowerCase()` before every comparison.

**Where the city match is enforced**: inside `Agent.tryAssign()`:
```java
if (!city.equals(lead.city())) return Optional.empty();
```

Since both `Agent.city` and `Lead.city` are `City` instances that were normalised at construction, the comparison is correct regardless of what casing arrived from the portal.

## Eligibility

> *"Whether a specific agent is a valid choice for a specific lead. An agent is eligible if they're active, serve the lead's city, and haven't hit their capacity limit."*

**Where it lives**: entirely inside `Agent.tryAssign()`.

The three conditions are checked in order:

```java
if (!active) return Optional.empty();                              // active check
if (!city.equals(lead.city())) return Optional.empty();           // city match
if (currentLoadInWindow >= MAX_LEADS_PER_WINDOW) return empty();  // capacity check
```

Each condition is independent. All three must pass. The method returns `Optional.empty()` for any ineligible agent and `Optional.of(assignment)` only when all three pass.

There is no `isEligible()` helper and no separate eligibility object. Eligibility is not a state — it is the result of evaluating three conditions at a point in time. `tryAssign()` combines the check and the production of the `Assignment` into a single atomic operation: you cannot check eligibility without simultaneously producing the assignment if the check passes.

The use case also pre-filters candidates before calling `tryAssign()` (filtering by `load < MAX_LEADS_PER_WINDOW`), but `tryAssign()` re-checks all three conditions independently — it is a second line of defence that enforces the rules even if a caller bypasses the pre-filter.

## Routing Decision

> *"The automatic choice of which eligible agent gets a given lead. When multiple agents are eligible, the one with the lightest current workload wins."*

**Primary class**: `domain/service/LeadRoutingService.java`

`LeadRoutingService` is a domain service — logic that doesn't naturally belong to a single aggregate. It receives a list of pre-filtered `AgentWithLoad` candidates and picks the best one.

```java
public Optional<AgentWithLoad> pickAgent(Lead lead, List<AgentWithLoad> candidates) {
    int minLoad = candidates.stream()
            .mapToInt(AgentWithLoad::currentLoad).min().orElseThrow();

    List<AgentWithLoad> tied = candidates.stream()
            .filter(c -> c.currentLoad() == minLoad).toList();

    return Optional.of(tied.get(tiebreaker.nextInt(tied.size())));
}
```

Step 1: find the minimum load. Step 2: collect all agents at that minimum. Step 3: pick one at random from the tied group. The glossary says "the one with the lightest workload wins" — the code implements this exactly, with random tiebreaking when multiple agents share the lightest load.

The `Random tiebreaker` is injected through the constructor, making the service deterministic in tests (`new Random(0)`) and non-deterministic in production (`new Random()`).

## Customer Contact

> *"The customer's name, email, and phone number — the information an agent needs to reach out."*

**Primary class**: `domain/model/CustomerContact.java`

```java
public record CustomerContact(String name, String email, String phone) {
    public CustomerContact {
        name = name.trim();                          // strip whitespace
        email = email.trim().toLowerCase(Locale.ROOT); // normalise email
        phone = phone.replaceAll("\\s", "");         // strip whitespace from phone
        // + length and format validation for each field
    }
}
```

Three normalisations happen at construction:
- Name is trimmed — leading/trailing whitespace from web forms is stripped
- Email is lowercased — email addresses are case-insensitive (RFC 5321), so `MARIO@EXAMPLE.COM` and `mario@example.com` are the same contact
- Phone has whitespace stripped — `+39 333 123 4567` becomes `+39333123456` for consistent storage

`CustomerContact` is a value object held by `Lead`. It is written to the `leads` table and read back when reconstituting a lead from the database. The agent notification receives `leadId`, `agentId`, and `city` — the contact details are in the `leads` row for the agent management system to look up.

## Notification

> *"The alert sent to an agent when they've been assigned a new lead. Handled by a separate system, but this service is responsible for making sure the hand-off happens reliably."*

**Domain event**: `domain/event/LeadAssignedEvent.java`

```java
public record LeadAssignedEvent(
        String eventId,
        String leadId,
        String agentId,
        String assignmentId,
        String city,
        String assignedAt,
        int schemaVersion
) implements DomainEvent {}
```

The glossary says "this service is responsible for making sure the hand-off happens reliably." The code enforces this through the transactional outbox: the event is persisted in the same database transaction as the assignment. If the notification system is down, the event survives in the `outbox_event` table and is retried by `OutboxRelay` until delivery succeeds (up to 5 attempts).

**Port interface**: `port/out/NotificationPort.java`

```java
public interface NotificationPort {
    void notify(LeadAssignedEvent event) throws NotificationDeliveryException;
}
```

The port interface is the boundary between this service and the "separate system" the glossary mentions. The current implementation (`InMemoryNotificationClient`) logs a structured line. In production this would be replaced by an HTTP call or a message broker publish — without changing the domain, the use case, or the outbox relay.
